8. Cortana / PME：语音助手从 POC 到 GA

这段经历证明你长期处理语音、跨语言桥接和会话可靠性。重点不是列 KWS/AEC/TTS 名词，而是讲清 Native/JS/Service 三侧的状态归属、流式播放、音频焦点和消息动作幂等。

8.1 系统边界

React Native UI / Conversation UX ↕ versioned native bridge CortanaModule / CatchMeUp Shell / UserStoreModule ├─ KWS / microphone / audio focus ├─ TTS streaming player ├─ Teams messaging actions └─ session/retry/telemetry ↕ Host SDK + Voice Service

状态真源：Native 拥有麦克风、播放器、audio focus 和宿主 messaging API；JS 拥有页面和产品交互；Service 拥有语义/会话结果。桥接协议必须显式，否则双方会各自猜测状态。

8.2 React Native Bridge Contract

data class BridgeCommand(
    val protocolVersion: Int,
    val sessionId: String,
    val commandId: String,
    val type: CommandType,
    val payload: JsonObject
)

data class BridgeEvent(
    val sessionId: String,
    val sequence: Long,
    val type: EventType,
    val payload: JsonObject
)
  • 每个 command 有 commandId，Like/Reply/Mark-as-Read 可去重。
  • 事件有 sessionId+sequence，JS 丢弃旧 session 或倒退 sequence。
  • Native module 方法不阻塞 UI thread；Promise 只返回接受结果，长任务通过事件更新。
  • 页面销毁时取消订阅，但 session 可由更长生命周期 owner 继续；重新订阅先发 snapshot 再发 delta。
  • 协议 version/capability 解决 JS bundle 与 Native host 版本不一致。

8.3 Voice Session 状态机

Idle → Starting → Listening → Processing → Speaking → Completed
          ↓           ↓           ↓          ↓
        Failed      Paused      Retrying   Interrupted

Audio focus loss: Speaking → Paused/Stopped
User barge-in:     Speaking → Interrupted → Listening
Network loss:      Listening/Processing → Retrying or Failed

UI 状态不能直接由按钮点击决定，而应由 session snapshot 驱动。所有异步 callback 在写状态前校验 session generation。退出页面、电话来电、蓝牙断开和 host account switch 都可能触发生命周期变化。

8.4 TTS Streaming

服务端按 chunk 返回文本或音频时，播放器需要控制 startup buffer、连续播放和取消。buffer 太小容易 underrun，太大增加 first audio latency。

问题处理
Chunk 乱序/重复sequence + request/session id；重复丢弃，缺口等待有限窗口
网络抖动自适应 startup buffer，监控 underrun
用户打断取消网络流、清播放器 buffer、递增 generation
Audio focus losspause/stop 并上报，恢复需产品规则
耳机切换监听 route，避免重建 session 时重复播放

8.5 Message Triage Actions

Like/Reply/Mark-as-Read 是有副作用的 tool action。语音识别结果不能直接执行：先解析目标 message/thread，必要时确认，再调用宿主 API。commandId 和 message version 保证 retry 幂等；unknown outcome 先查询当前状态。

拷打：Mark-as-Read 重试不是天然安全吗？
目标状态本身幂等，但调用可能作用在错误或过期 message，且 telemetry/副作用不一定幂等。仍需稳定 entity id、session context 和结果查询。

8.6 KWS、AEC 与隐私

  • KWS 持续监听与正式语音上传是两条边界；唤醒前数据应尽量本地处理。
  • AEC 需要参考播放信号；Audio route 和系统/软件双重 AEC 会影响效果。
  • 麦克风指示、权限、后台政策和明确用户反馈必须一致。
  • 误唤醒率、漏唤醒率、唤醒到 ready 延迟与电量是相互制约的指标。

8.7 Hermes 与 SDX 迁移

Hermes 预编译 bundle 减少 JS parse/compile 启动成本，但增加 build pipeline、source map 和版本兼容要求。SDX 迁移把 feature 从旧宿主耦合中抽离为可部署单元，Gov Cloud 又要求 endpoint、auth、telemetry 和依赖均可配置，不能硬编码 commercial cloud。

8.8 指标与测试

  • Wake-to-listening、first TTS audio、buffer underrun、session completion。
  • Bridge command latency、duplicate/stale event、JS/Native protocol mismatch。
  • Like/Reply/Mark-as-Read success/unknown outcome。
  • 故障注入：JS reload、Activity recreate、audio focus loss、蓝牙切换、网络中断、旧 callback 晚到。

8.9 口述版本

Catch Me Up 从 POC 到 GA 的难点是把语音 session、React Native UI 和 Teams 宿主动作连接成可恢复的系统。我把音频和 host capability 保留在 Native，JS 负责产品 UX，并通过带 session、sequence 和 commandId 的桥接协议避免旧事件和重复动作。Play My Email 的 TTS streaming 则围绕 first audio 与 underrun 做 buffer 取舍，并处理 audio focus、打断和网络恢复。Hermes/SDX 迁移进一步解决启动成本、模块部署和 Gov Cloud 配置差异。

8.10 POC→GA 的 Senior 证据

  • 列出你亲自 owner 的 native modules、bridge methods 和 host API。
  • 准备一个 JS/Native lifecycle race：旧 callback、页面销毁或 duplicate action。
  • 准备 TTS 指标定义：first audio、underrun、completion、interrupt。
  • 说明 POC 到 GA 新增了哪些非功能要求：telemetry、accessibility、Gov、rollback、support。
  • 说明 332 个 work item 里哪些体现 scope，而不是用数量替代影响。
三级追问：你说主导从 POC 到 GA
  1. 一级：GA 相比 POC 多了什么？
  2. 二级：你具体 owner 哪些模块、设计和 rollout？
  3. 三级：讲一个 GA blocker、失败方案、跨团队冲突和最终指标。答不出第三层时，“主导”会被质疑。
