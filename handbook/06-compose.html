5. Outlook Search：Java/View → Kotlin/Compose

问题
存量 Java/View 搜索由多个 Tab、Fragment/Adapter、回调和宿主导航耦合。状态散落，Tab 切换可能重复请求或丢失数据；一次性重写风险高，且不能破坏 telemetry、企业策略和旧宿主。
策略
先迁移“状态和边界”，后迁移 UI：定义 Kotlin domain model、SearchRepository、UiState/Action/Effect；用 ViewModel 形成单向数据流；通过 ComposeView 或 AndroidView 与旧页面共存；逐 Tab feature flag 替换。
性能
baseline 对比冷启动、首屏、搜索结果首条出现、滚动帧、recomposition、内存与错误率。使用稳定 key、immutable model、derivedStateOf、分页、避免在 composition 中启动请求；用 Macrobenchmark/Profile 验证。
结果
统一 People/Files/Events 状态模型，降低 UI 与数据源耦合，支持可恢复 Tab 状态、测试和渐进 rollout。待补数：Java/Compose 首屏、jank、重复请求、代码量/测试覆盖率。

推荐状态模型

data class SearchUiState(
    val query: String = "",
    val selectedTab: SearchTab = SearchTab.People,
    val tabs: Map<SearchTab, TabState> = SearchTab.entries.associateWith { TabState.Idle }
)
sealed interface TabState {
    data object Idle : TabState
    data object Loading : TabState
    data class Content(val items: List<SearchItem>, val nextPage: String?) : TabState
    data class Error(val kind: ErrorKind, val canRetry: Boolean) : TabState
}
sealed interface SearchAction {
    data class QueryChanged(val value: String) : SearchAction
    data class TabSelected(val tab: SearchTab) : SearchAction
    data object Retry : SearchAction
}

为什么不能全量重写

  • 搜索是高流量入口，行为兼容和回滚比代码洁癖重要。
  • 旧宿主、导航、企业策略、埋点和 A/B 实验仍依赖既有 contract。
  • 渐进迁移能逐 Tab 对比，快速隔离 regression；代价是过渡期有双栈和 adapter。

Compose 性能拷打

如何避免无效重组？

缩小 state 读取范围；稳定/不可变模型；LazyColumn 使用稳定 key；高频派生值用 derivedStateOf；回调用 rememberUpdatedState；不要每次 composition 创建集合或启动 IO。

Compose 比 View 一定快吗？

不一定。Compose 改善开发模型，但错误的 state 粒度、对象分配、布局层级和图片加载同样会造成 jank。必须用 Macrobenchmark、JankStats、Layout Inspector/Recomposition counts 和真实设备数据证明。

5.1 旧架构的问题画像

Java/View 版本常见结构是 Activity/Fragment 持有多个 Tab controller，Adapter、Loader/Callback 和导航相互引用。Query、selected tab、loading、results、error 分散在字段和 Bundle 中，导致旋转/进程恢复、快速切 Tab、重复请求和过期 callback 难以推理。

Legacy Fragment ├─ mutable query / selectedTab ├─ PeopleAdapter + callbacks ├─ FilesAdapter + callbacks ├─ EventsAdapter + callbacks ├─ Navigation / Telemetry └─ Host policy 目标：UI → Action → ViewModel/Reducer → State → UI ↓ Repository / UseCases ↓ versioned result + cancellation

5.2 渐进迁移的 Strangler Strategy

  1. 先记录旧版 baseline：首屏、搜索 latency、jank、错误和 telemetry 事件。
  2. 抽取 Kotlin domain model 与 repository interface，旧 View 和新 Compose 共用。
  3. 建立 ViewModel/reducer，让旧 UI 也可订阅统一 state，消除双状态真源。
  4. 用 ComposeView 替换单个 Tab 或 result block，而不是整页 big bang。
  5. 导航、policy 和 telemetry 通过 adapter 保持 contract。
  6. Feature Flag 双轨，对同一实验维度比较；稳定后删除旧路径和 adapter。

过渡期最大的风险是“双写”：旧 controller 和新 ViewModel 都更新 query/results。必须规定唯一 owner，interop layer 只做翻译，不持有业务状态。

5.3 搜索并发语义

class SearchViewModel(
    private val repository: SearchRepository,
    savedState: SavedStateHandle
) : ViewModel() {
    private val query = savedState.getStateFlow("query", "")
    private val selectedTab = savedState.getStateFlow("tab", SearchTab.People)

    val state: StateFlow<SearchUiState> = combine(query, selectedTab) { q, tab -> q to tab }
        .debounce(250)
        .distinctUntilChanged()
        .flatMapLatest { (q, tab) ->
            if (q.isBlank()) flowOf(SearchUiState.Empty(tab))
            else repository.search(tab, q)
                .map<SearchPage, SearchUiState> { SearchUiState.Content(tab, q, it) }
                .onStart { emit(SearchUiState.Loading(tab, q)) }
                .catch { emit(SearchUiState.Error(tab, q, classify(it))) }
        }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), SearchUiState.Initial)
}
  • flatMapLatest 取消旧 query，但底层 HTTP 是否真正取消需 repository 支持。
  • 结果携带 query/tab/generation，旧结果无法写入新状态。
  • 每个 Tab 是否保留独立结果取决于产品；可用 map<Tab,TabState>，但需内存预算。
  • SavedState 保存 query/tab/必要 cursor，不保存整页大量结果；进程恢复从 cache/repository 重建。

5.4 Compose 互操作与生命周期

composeView.setViewCompositionStrategy(
    ViewCompositionStrategy.DisposeOnViewTreeLifecycleDestroyed
)
composeView.setContent {
    val state by viewModel.state.collectAsStateWithLifecycle()
    SearchTabContent(state, onAction = viewModel::dispatch)
}

Fragment view lifecycle 与 Fragment lifecycle 不同；错误策略会导致 composition 在 onDestroyView 后仍存活。Navigation 和 Activity Result 通过事件/launcher 处理，不把 Activity 引用放入 ViewModel。

5.5 Lazy 列表与重组

LazyColumn {
    items(
        items = state.items,
        key = { it.stableId },
        contentType = { it.type }
    ) { item ->
        SearchResultRow(
            item = item,
            onClick = remember(item.stableId) { { onOpen(item.stableId) } }
        )
    }
}
  • 稳定 key 保持 item identity；index 作为 key 会让插入/排序引发状态错位。
  • 只向 Row 传必要 immutable model，避免整个 screen state 变化导致所有 Row 重组。
  • 图片提供固定尺寸和缓存；富文本 parse 在后台或预处理。
  • 分页 append 与 refresh 状态分离，避免 footer 更新影响全部 item。

5.6 Telemetry 兼容

迁移不能让指标“变好”只是因为事件少报。定义统一 semantic event，由旧 View 和 Compose adapter 发送同一 schema；去重 key 包含 session/query/tab/result impression。页面曝光应基于可见性，不是 Composable 被调用。

5.8 Rollout 与回滚

按 Tab 或用户 flight，而不是随机混用同一页面的多个实现。监控 crash/ANR、search success、zero-result、TTFD、jank 和 telemetry volume。Feature flag 必须能在不发版情况下回旧 View；数据库/schema 改动需保持双读兼容。

5.9 口述版本

我没有把 Outlook Search 当成一次 UI 重写，而是用 strangler strategy 渐进迁移。先把 Java/View 中分散的 query、tab 和 result 抽成 Kotlin domain/repository 和单向 state，再让旧 UI 与 Compose 共用同一状态真源，随后按 Tab 通过 ComposeView 替换。搜索用 debounce、flatMapLatest 和 generation 解决旧请求晚到；列表用稳定 key、细粒度 state 和后台预处理控制 jank。旧新路径发送同一 telemetry schema，并在 feature flag 下比较首屏、滚动、错误和请求重复，确保指标改善不是漏报造成。
