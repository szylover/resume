6. OCM Runtime：可靠性、图片、渲染与 Context Pipeline

本章对应简历中 OCM 的四项基础能力。面试时不能只说“做了 Runtime”，必须能从用户症状、状态机和代码讲到指标、故障注入、灰度与取舍。

6.1 弱网与会话可靠性

用户问题和工程目标

移动网络不是简单的“在线/离线”：Wi-Fi 可能有链路但无法访问互联网，DNS 可能短暂失败，TCP/TLS 可能建立失败，WebSocket 可能半开，服务端可能已处理请求但响应丢失。目标是区分故障层级，避免盲目重试，同时保证会话状态不重复、不倒退。

UI / Conversation ↓ intent with requestId / turnId Session State Machine ↓ Retry & Recovery Policy ├─ Network availability / validated capability ├─ DNS / connect / TLS / HTTP / WebSocket classification ├─ Idempotency + retry budget └─ session rebuild / resume / fail-fast ↓ Transport + Telemetry

错误分类

故障判断处理不能做什么
NetworkUnavailable无 validated network进入 WaitingForNetwork；网络回来后恢复立即高频 retry
DNS temporary failureUnknownHost/解析超时，网络本身可用指数退避+jitter，必要时 fresh connection无限重试或把它归为服务端 5xx
Connect/TLS failuresocket connect、证书、pinning可重试连接错误与不可重试安全错误分离对 pinning failure fallback 到不安全通道
HTTP 401/403token/权限刷新凭据一次或要求重新登录用普通 retry budget 反复请求
HTTP 429/503限流/服务暂不可用尊重 Retry-After，全局预算和熔断所有客户端同时立即重试
WebSocket half-open无 close callback，但 heartbeat/ack 超时标记 suspect→reconnect/resume继续向旧 socket 写入并假设成功
Unknown outcome请求发送后连接断开，不知服务端是否处理用 requestId 查询/去重生成新 id 重复执行

会话状态机

sealed interface SessionState {
    data object Idle : SessionState
    data class Connecting(val attempt: Int) : SessionState
    data class Connected(val sessionId: String, val networkEpoch: Long) : SessionState
    data class Recovering(val sessionId: String?, val reason: FailureKind) : SessionState
    data class WaitingForNetwork(val lastSessionId: String?) : SessionState
    data class Failed(val kind: FailureKind, val canRetry: Boolean) : SessionState
}

sealed interface FailureKind {
    data object NetworkUnavailable : FailureKind
    data object DnsTemporary : FailureKind
    data object ConnectTimeout : FailureKind
    data object AuthExpired : FailureKind
    data object PolicyRejected : FailureKind
    data object ServerThrottled : FailureKind
    data object UnknownOutcome : FailureKind
}

状态真源：Service/Session manager 持有连接状态，Compose UI 只订阅；不能让多个页面各自判断“是否已连接”。每个 callback 都带 generation/sessionId，旧连接晚到的事件不得覆盖新连接。

Retry Policy

data class RetryDecision(
    val retry: Boolean,
    val delayMs: Long = 0,
    val rebuildSession: Boolean = false,
    val waitForNetwork: Boolean = false
)

fun decideRetry(
    failure: FailureKind,
    attempt: Int,
    retryAfterMs: Long?,
    budgetRemaining: Int
): RetryDecision = when {
    budgetRemaining <= 0 -> RetryDecision(false)
    failure is FailureKind.PolicyRejected -> RetryDecision(false)
    failure is FailureKind.AuthExpired && attempt == 0 ->
        RetryDecision(true, rebuildSession = true)
    failure is FailureKind.NetworkUnavailable ->
        RetryDecision(true, waitForNetwork = true)
    failure is FailureKind.ServerThrottled ->
        RetryDecision(true, delayMs = retryAfterMs ?: 5_000)
    failure is FailureKind.DnsTemporary || failure is FailureKind.ConnectTimeout ->
        RetryDecision(true, delayMs = exponentialBackoffWithJitter(attempt), rebuildSession = true)
    failure is FailureKind.UnknownOutcome ->
        RetryDecision(false) // query by request/operation id instead
    else -> RetryDecision(false)
}

Backoff：min(cap, base * 2^attempt) 后加入 full jitter。预算既包括次数也包括总时间；前台用户等待和后台恢复使用不同预算。网络恢复事件可以提前唤醒 WaitingForNetwork，但不应让所有请求同时冲击服务端。

Telemetry 与 SLO

  • Session setup success、resume success、unexpected disconnect。
  • 按 DNS/connect/TLS/auth/HTTP/WebSocket/application 分类的失败率。
  • Retry attempt distribution、budget exhausted、reconnect loop。
  • 用户体验：time-to-first-content、恢复耗时、重复消息、丢 turn。
  • 维度：network type、validated/metered、app/sdk version、host、region、error taxonomy；避免 PII。
拷打：弱网恢复为什么不能只用 ConnectivityManager 检测 online？
Network callback 只能说明系统网络能力，不能保证 DNS、目标 endpoint、TLS、WebSocket 和业务 session 都健康。它用于调度恢复，不是成功证明；最终需要分层请求结果和 heartbeat/ack。
拷打：如何避免 reconnect storm？
指数退避+jitter、全局 retry budget、按 endpoint 熔断、尊重 Retry-After、网络恢复后随机扩散，并让同一 session 的并发调用 single-flight。

6.2 图片上传与隐私链路

三条入口不是同一件事

入口Android 细节风险
Gallery / Photo Picker优先系统 Photo Picker；返回 content URIURI 权限可能短期有效，不能假设永久路径
CameraFileProvider 预创建输出 URI；处理取消与空文件相机权限、临时文件清理、方向信息
Image Edit / Share接收外部 URI、MIME 和 grant flag不可信 provider、超大文件、伪造 MIME、读取权限过期

端到端 pipeline

Select / Capture / Share → Validate URI + MIME + size → Consent Gate → Decode bounds (not full bitmap) → EXIF orientation + metadata policy → Resize / compress / transcode → Encrypt temporary upload artifact → Obtain upload session → Chunked upload + progress → Server scan / DLP / moderation → Attach reference to Copilot turn → Cleanup temporary data

不能把 content URI 转成所谓“真实文件路径”。应通过 ContentResolver 流式读取。先 decode bounds，再按目标尺寸计算 sample，避免把 50MP 图片完整解码造成 OOM。EXIF 可能包含 GPS、设备和拍摄时间，应按隐私策略移除或保留。

Consent 状态模型

data class ConsentKey(
    val userId: String,
    val tenantId: String,
    val policyVersion: String,
    val purpose: UploadPurpose
)

sealed interface UploadState {
    data object Idle : UploadState
    data class AwaitingConsent(val items: List<PendingImage>) : UploadState
    data class Preparing(val completed: Int, val total: Int) : UploadState
    data class Uploading(val uploadId: String, val sent: Long, val total: Long) : UploadState
    data class Processing(val attachmentId: String) : UploadState
    data class Ready(val attachmentId: String) : UploadState
    data class Failed(val stage: Stage, val retryable: Boolean) : UploadState
}

enum class Stage { VALIDATION, CONSENT, DECODE, TRANSFORM, UPLOAD, SERVER_SCAN }

Consent 必须绑定用户、tenant、purpose 和 policy version。用户同意“为当前对话上传”不代表永久允许后台上传，也不能跨企业/个人账号复用。政策升级或作用域变化后重新询问。

上传可靠性

  • 大文件使用 upload session + chunk offset，重试同一 chunk 时必须幂等。
  • 本地只保存 uploadId、offset 和加密临时文件引用；不要保存 bearer token。
  • 进程死亡后 WorkManager 可恢复明确批准的上传，但 consent 过期或账号变化必须停止。
  • HTTP timeout 后查询 server committed offset，不能假设 chunk 未写入。
  • 用户取消时 cancel server session、删除临时文件，并确保 UI 不再附加旧 attachment。

安全拷打

如何防止恶意 URI？

只通过 ContentResolver 读取；验证 scheme、MIME magic bytes、尺寸、解码预算和总字节；不信任文件名与扩展名；捕获 provider 在读取中途撤销权限；不执行任何嵌入内容。

图片压缩放在哪一端？

客户端缩放可省带宽和延迟，但消耗 CPU/电量并可能影响质量；服务端转换一致性更好。常见方案是客户端做上限约束和预压缩，服务端做最终规范化、扫描和多尺寸派生。

Consent 和 Android permission 有什么区别？

系统 permission 决定 App 能否访问资源；产品 consent 说明数据将用于什么目的、发送到哪里。获得 URI 权限不等于用户同意上传给 AI 服务。

6.3 Rich Response / Artifacts 页面性能

先定义“卡顿”

卡顿可能来自主线程长任务、过度重组、Lazy 列表 item 不稳定、Markdown/代码高亮、图片 decode、WebView/Artifact、流式 token 高频更新或 GC。必须用指标分层定位，而不是看到 Compose 就说 recomposition。

指标说明
TTFC / First Render进入页面到首个可用内容
Frame duration / jank超过设备刷新周期的帧；看 P95/P99 和 jank ratio
Recomposition count诊断信号，不是最终用户指标
Main-thread slicesMarkdown parse、JSON mapping、bitmap decode、layout
Memory/GC大对象、图片、缓存和流式字符串复制

常见反模式

// 反模式：每个 token 都复制完整字符串并让整页读取同一 state
uiState.update { it.copy(answer = it.answer + token) }

// 改进：transport 层批处理；UI 按稳定 block 更新
flow.buffer()
    .chunkedByTime(windowMs = 50)
    .map { tokens -> tokens.joinToString("") }
    .onEach { delta -> reducer.appendToBlock(blockId, delta) }
  • 状态按 message/block 粒度拆分，避免页面根节点读取不断变化的完整 response。
  • LazyColumn 使用稳定 key 与 contentType；domain model 尽量 immutable/stable。
  • Markdown parse、syntax highlight、JSON→UI model 在后台线程完成，主线程只提交结果。
  • 流式更新按 16–100ms 窗口合并；太快只增加重组，太慢会损失“实时”感。
  • 图片先显示固定比例 placeholder，使用尺寸合适的 decode，防止加载后大范围 relayout。
  • Artifact/WebView 与 Compose 之间限制高频 bridge 消息，生命周期结束立即释放。

状态与 reducer

@Immutable
data class ResponseBlock(
    val id: String,
    val type: BlockType,
    val content: BlockContent,
    val version: Long
)

@Immutable
data class RichResponseState(
    val orderedIds: List<String>,
    val blocks: PersistentMap<String, ResponseBlock>
)

fun reduceDelta(state: RichResponseState, delta: BlockDelta): RichResponseState {
    val previous = state.blocks[delta.blockId]
    val next = applyDelta(previous, delta)
    if (next == previous) return state
    return state.copy(blocks = state.blocks.put(delta.blockId, next))
}

结构共享减少无关 block 的对象变化。UI item 只订阅自己的 block；滚动状态与 response content 分离。对超长对话设置 windowing、分页或历史 block 降级，避免所有富内容常驻内存。

性能验证流程

  1. 定义基线场景：冷启动、100 条消息、持续 streaming、代码块、图片和 Artifact。
  2. Macrobenchmark 测 startup/scroll；JankStats/Perfetto 看长帧和主线程 slice。
  3. Compose Layout Inspector 看重组范围，但最终以帧和用户指标为准。
  4. 优化一次只改一个变量，通过 feature flag/A-B 对比低中高端设备。
  5. 护栏：crash/ANR、内存峰值、GC、耗电、首屏、错误渲染和无障碍。
拷打：减少 recomposition 就一定更快吗？
不一定。重组可能很便宜，真正瓶颈可能是 measure/layout、draw、图片、Markdown parse 或主线程 IO。重组次数只是线索，必须用 Perfetto/frame metrics 验证。

6.4 AI Context Pipeline

为什么需要结构化 Context

用户在 Outlook 选择一封邮件、在 Office 选择一段文档时，模型需要的不只是文本，还包括实体类型、来源、权限、引用范围、时间和稳定标识。结构化 annotation 让模型/服务知道“这是什么”和“能否使用”，并支持审计、去重、截断与跨宿主协议兼容。

data class ContextEntity(
    val entityId: String,
    val type: EntityType,
    val displayTitle: String,
    val contentRef: SecureContentRef,
    val selectedRange: TextRange?,
    val provenance: Provenance,
    val permissions: PermissionSnapshot,
    val sensitivity: SensitivityLabel?,
    val estimatedTokens: Int,
    val version: String
)

data class ContextEnvelope(
    val schemaVersion: Int,
    val conversationId: String,
    val entities: List<ContextEntity>,
    val userIntent: String,
    val totalTokenBudget: Int
)

Pipeline

Host Selection → Normalize host-specific object → Resolve stable entity + permission → Fetch minimum necessary content → Sanitize / injection labeling → Deduplicate and rank → Apply token budget / truncation → Decorate with provenance and citations → Serialize versioned annotation → Inject after host decoration → Audit metadata (not raw content)

Token Budget 与截断

不能简单按字符串尾部截断。先给 system/user instruction 留预算，再按用户显式选择、当前实体、最近相关实体排序。邮件应保留 subject/from/date/thread relation；文档应按段落/标题边界裁剪。被截断时携带标记，避免模型误以为内容完整。

策略优点风险
按字符截断实现简单破坏语义边界、token 估计不准
按段落/消息保留结构单块过大，需要二次摘要
先摘要再注入节省 token摘要可能丢事实；需要 provenance
检索式按需加载规模更大增加延迟、权限和检索误差

权限和 Prompt Injection

  • 客户端选择不是授权证明；服务端按当前用户/tenant 重新校验。
  • 权限 snapshot 有 TTL；分享状态变化、账号切换后必须失效。
  • 邮件/文档中的“忽略系统指令”被标记为 untrusted content，不能提升为 instruction。
  • context 中的 URL、附件和嵌入对象按 allowlist 解析，不能让模型任意 fetch。
  • 审计记录 entity id、类型、policy/schema version 和使用结果，原文最小化。

Schema 演进

跨 OfficeMobile、Outlook、Teams 的 SDK 必须面对宿主版本不一致。Envelope 带 schemaVersion；新增字段向后兼容，未知 entity type 可降级为 generic reference；breaking change 通过 capability negotiation/feature gate。序列化测试使用 golden files，并验证旧 host、新 SDK 和新 service 的组合矩阵。

缓存与性能

  • 缓存 key 包含 entity/version/user/tenant/permission epoch，禁止跨账号复用。
  • 只缓存加密引用或必要摘要；敏感原文遵循宿主数据策略。
  • 并行 resolve 多个实体，但设置总并发和 deadline；部分失败可显示缺失来源，不阻塞全部请求。
  • 指标：context_build latency、permission failure、token utilization、truncation、dedupe ratio、grounding/citation success。
拷打：为什么不直接把选中文字拼进 prompt？
拼文本丢失 entity、provenance、权限、版本和截断语义，也无法安全演进跨宿主协议。结构化 annotation 让模型输入可审计、可预算、可去重，并允许服务端重新授权。

如果无法公开内部指标怎么办？

给出指标定义、分桶、实验和护栏，不给虚假绝对数；可说明“内部数值不公开”。但至少准备趋势、是否达到 rollout gate、是否回滚及一个具体故障，否则仍显空泛。
