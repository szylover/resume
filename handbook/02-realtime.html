1. Realtime Voice：WebSocket → WebRTC

背景
旧链路把 PCM/Base64 音频块、控制信号、transcript 等耦合在 SignalR/WebSocket 上。客户端承担采集、buffer、播放和状态推断；TCP 队头阻塞、网络切换、回声/降噪和打断体验都难以系统治理。
你的目标
主导 Android 端 transport migration，同时保持 shared conversation state、宿主接口和 rollout 可控；最终让用户更快能说、少丢开头、少出现“有字没声”、打断自然、后台和弱网更稳定。
核心设计
音频走 WebRTC media plane（RTP/Opus、jitter buffer、AEC/NS）；join、mute/unmute、transcript、telemetry 等走 Data Channel/control plane；不同 transport 的物理信号统一映射为 Listening/Speaking/Interrupted 等共享状态。
UI / Shared Voice State ↑ SydneyRealtimeChatService ↑ RealtimeChatClient interface ↙ ↘ WebSocket Client WebRTC Client ├─ Media Channel: mic/speaker/RTP ├─ Data Channel: control/transcript ├─ Warmup & session lifecycle └─ Speaking/FAR/Barge-in handler

必须讲清的技术点

问题方案Trade-off
为什么不只替换 socket媒体与控制分离；重构状态来源、buffer 和 telemetry 语义双栈 rollout 期间复杂度上升，需要清晰抽象边界
Speaking 如何识别WebRTC 不再收到 audio chunk；使用 speaker output level，经阈值、silence window、dead period 转换为状态output level 更接近用户实际听到，但受设备、音量和噪声影响
如何做打断把 output speaking、user input、completion 与 server signal 合并成确定性状态机阈值太敏感会误打断；太保守则用户感觉迟钝
为什么旧指标不能直接复用WebSocket 起点是 chunk arrival；WebRTC 起点可能是系统实际播放，包含 decode/jitter/playback历史趋势断层；需同时上报 transport-specific 与统一业务时间点
经历边界：你已说明没有亲自交付 WebRTC 迁移，因此本章用于协议学习、架构分析和原型设计。面试中可以说“系统研究并设计过方案”，不能说“主导生产迁移”或引用并不存在的上线指标。

1.1 协议栈全景

Application: Conversation / Transcript / Agent State ├─ Control: WebRTC DataChannel │ └─ SCTP → DTLS → ICE/UDP (or TURN relay) └─ Media: Audio Track └─ Opus → RTP / RTCP → SRTP → ICE/UDP Signaling（不属于 WebRTC 标准传输本身） └─ HTTPS/WebSocket: token、SDP offer/answer、ICE candidates、session control

最容易答错的一点：WebRTC 没有规定 signaling 必须用什么。客户端仍需通过 HTTPS、WebSocket 或业务服务交换 SDP、ICE candidate、token 与 session metadata。WebRTC 规定的是媒体、连接、安全和数据通道等机制。

协议/组件职责面试关键词
SDP描述能力与参数，不负责真正传输媒体codec、payload type、ICE ufrag/pwd、fingerprint、media direction
ICE收集并检查候选网络路径，选出 candidate pairhost/srflx/relay、connectivity check、nomination
STUN发现 NAT 映射后的公网地址server-reflexive candidate；不是媒体中继
TURN直连失败时中继媒体/数据可靠但增加 RTT、成本和带宽
DTLS握手、身份验证和密钥协商证书 fingerprint 从 SDP 校验
SRTP加密 RTP/RTCP 媒体DTLS-SRTP 导出密钥；防窃听和篡改
RTP/RTCP实时媒体与质量反馈sequence/timestamp/SSRC、loss/jitter/RTT
SCTP/DataChannel可靠或部分可靠的应用数据ordered/unordered、maxRetransmits、stream

1.2 从点击 Voice 到听到第一句话

  1. 业务鉴权：客户端取得短期 token、session 配置、feature flags 和服务 endpoint。
  2. 创建 PeerConnection/媒体 client：初始化 audio device module、采集/播放线程与 peer connection factory。
  3. 本地媒体：创建 audio track，设置 send/receive direction；Android 申请/占用音频焦点并配置 communication mode。
  4. SDP 协商：一方 createOffer/setLocalDescription，业务 signaling 发送 offer；另一方 setRemoteDescription/createAnswer，再返回 answer。
  5. ICE gathering：产生 host、STUN 获得的 srflx、TURN relay candidates；Trickle ICE 可边收集边发送，减少等待。
  6. Connectivity checks：候选对之间进行 STUN Binding checks；ICE controller 选择并 nominate 最佳可用 pair。
  7. DTLS：在选定路径上握手，验证 SDP fingerprint，并导出 SRTP key。
  8. Media/Data ready：RTP/Opus 开始收发；DataChannel 进入 open；业务 SetupAndJoin 完成。
  9. 用户可感知 ready：不能只以 ICE connected 判断，还需 mic、media session、server conversation 都 ready。
  10. FAR：服务端生成回答，经网络、jitter buffer、decode 和 AudioTrack 输出；speaker output level 才接近“用户实际听到”。
追问：ICE connected 是否等于通话可用？
不等于。它只说明候选路径 connectivity check 成功。DTLS、SRTP、DataChannel、服务端 join、麦克风权限、audio route 和实际双向媒体仍可能失败，因此需要分层 readiness。

1.3 SDP Offer/Answer 该会到什么程度

v=0
o=- 461173305279927 2 IN IP4 127.0.0.1
s=-
t=0 0
a=group:BUNDLE 0 1
m=audio 9 UDP/TLS/RTP/SAVPF 111
c=IN IP4 0.0.0.0
a=mid:0
a=sendrecv
a=rtpmap:111 opus/48000/2
a=fmtp:111 minptime=10;useinbandfec=1
a=ice-ufrag:abcd
a=ice-pwd:long-random-secret
a=fingerprint:sha-256 12:34:...
a=setup:actpass
m=application 9 UDP/DTLS/SCTP webrtc-datachannel
a=mid:1
a=sctp-port:5000
  • m=audio 宣告音频 media section；111 是动态 payload type，对应 Opus。
  • BUNDLE 允许多个 media section 复用一条 ICE/DTLS transport。
  • sendrecv 表示双向；也可能是 sendonly/recvonly/inactive。
  • ice-ufrag/pwd 用于 ICE connectivity check 鉴权，不是用户凭据。
  • fingerprint 绑定 DTLS 证书，防止中间人替换。
  • application + SCTP 描述 DataChannel。

Renegotiation：添加 track、改变方向或 ICE restart 可能触发新 offer/answer。双方同时发 offer 会产生 glare；常见处理是 perfect negotiation pattern 或由一侧固定承担 offerer。

1.4 ICE、NAT、STUN、TURN

Candidate 类型

  • host：设备本地接口地址，速度最好，但跨 NAT 常不可达。
  • server-reflexive：STUN 看到的公网映射地址，允许 NAT traversal。
  • peer-reflexive：connectivity check 中发现的新映射。
  • relay：TURN 中继地址，成功率高但成本和 RTT 更高。

ICE 不是简单“按 host→srflx→relay 尝试”。它构造 candidate pair、计算 priority、并行/分批进行 STUN check，最后 nomination。企业防火墙、对称 NAT、UDP 被禁时往往需要 TURN/TCP 或 TURN/TLS。

追问：为什么不永远走 TURN？
TURN 提高可达性，但所有流量经过中继，增加 RTT、服务器带宽成本、区域容量和故障面。通常优先直连，必要时 relay；对企业网络可调整候选策略。

网络切换

Wi-Fi→蜂窝会改变本地网络与 NAT 映射。实现可选择等待 ICE 自恢复、ICE restart、或重建 peer/session。决策依据包括断开持续时间、服务端是否支持 resume、旧 DataChannel 状态、凭据有效期和用户是否仍在通话。

1.5 RTP、RTCP 与 Opus

  • RTP sequence number：检测丢包和重排；不能单独代表播放顺序。
  • RTP timestamp：按媒体时钟采样，用于播放时间线和 jitter 计算，不是 wall clock。
  • SSRC：标识同步源；切换源或重连时可能改变。
  • RTCP：报告 packet loss、jitter、RTT、接收统计；发送/接收端用它调整码率和诊断。
  • Opus：适合语音和音乐，支持可变码率、DTX 和 in-band FEC；参数需要在质量、带宽、CPU 和延迟间权衡。
  • Jitter buffer：吸收网络抖动；更大 buffer 更稳但增加交互延迟，实时对话必须动态平衡。
  • NACK/重传：对很短实时窗口有用；太晚到达的包即使重传也无播放价值。
  • FEC/PLC：前向纠错和丢包隐藏可改善小比例丢包，但会增加码率或降低保真。
追问：WebRTC 为什么比 WebSocket 更适合音频？
不是因为 UDP 永远更快，而是媒体栈同时提供 RTP 时间语义、jitter buffer、丢包反馈、拥塞/码率适配、AEC/NS、设备路由和 NAT traversal。WebSocket/TCP 保序会让单包丢失阻塞后续音频，实时媒体更重视及时性而非每字节必达。

1.6 Data Channel 设计

DataChannel 基于 SCTP over DTLS。可配置 ordered/unordered 和可靠性。控制消息不能全部使用同一策略：

消息建议原因
Join / policy / final transcriptordered + reliable不能乱序或丢失
Mic mute/unmuteordered + reliable，带 monotonically increasing version最终状态必须一致，旧消息不能覆盖新状态
实时音量/typing indicatorunordered + partial reliability旧值过期，无需阻塞新值
Heartbeat可丢、带 timestamp/sequence用于活性判断而非业务事实

所有业务消息应有 schema version、sessionId、turnId、messageId、timestamp，并定义去重与未知字段兼容。DataChannel open 不代表业务 join 完成。

1.7 对照整理文档：Android 迁移的十个具体模块

  1. Early Connection / Warmup / SetupAndJoin：把可预测的 SDK、token、client、DataChannel 初始化前移，合并 create/configure/join 往返。
  2. Warmup failure detection：isWarmUpFailed() 或更完整 health contract；失败、MediaStreamSession disconnected 后不可复用，Service 重建 client。
  3. Rewarmup after close：session 关闭后按场景重新预热，但必须控制电量、TTL 和无效命中。
  4. Audio Burst buffering：连接未 fully ready 时缓存用户最初语音，避免第一句话开头丢失；需要最大时长、内存上限和超时丢弃策略。
  5. Data Channel warmup/reuse：提前初始化 join channel，减少真实点击时重复建链。
  6. Mute/unmute control：通过 DataChannel 明确通知服务端，不能用“没有音频包”猜测用户 mute。
  7. Speaking/FAR：WebRTC 不经过旧 audio chunk callback，使用 ACS speaker output level 映射 Speaking 和 First Audio Render。
  8. Barge-in：处理 volume threshold、silence、completion dead period 和异常 audio-start，避免 bot 刚结束又被误判 speaking。
  9. Background/Mixed Modality：RealtimeKeeper 保持会话，处理后台限制、audio focus、通知、Voice/Text context continuity。
  10. Reconnect/Error Taxonomy：ACS reconnect、fresh REST connection、DNS backoff、NetworkUnavailable 分类，并映射统一 CIE error。

1.8 Android 音频系统必须会答

  • Audio focus：请求 transient/exclusive 或 communication 合适的 focus；处理其他应用抢占、duck 和 loss。
  • Audio mode：MODE_IN_COMMUNICATION 影响 AEC、路由和音频处理；进入退出必须成对。
  • Route：speaker、earpiece、有线、Bluetooth SCO/LE Audio；切换会改变采样、延迟和设备状态。
  • Permissions：RECORD_AUDIO；后台持续采集通常需要 foreground service、明确通知和平台政策合规。
  • AEC/NS/AGC：硬件、系统、WebRTC 软件处理可能重复；双重处理会产生失真，必须明确谁拥有处理链。
  • 生命周期：Activity 销毁不应直接终止 session；但用户退出、账号切换和权限撤销必须立刻释放 mic。

1.9 Speaking、FAR 与 Barge-in 状态机

Idle
 ├─ userStart → Connecting
Connecting
 ├─ mediaReady + joined → Listening
 └─ timeout/error → Failed
Listening
 ├─ userAudio → UserSpeaking
 └─ serverResponseStarted → WaitingForBotAudio
WaitingForBotAudio
 ├─ outputLevel > threshold for debounce → BotSpeaking + FAR
 └─ responseCompleted without audio → Completed/NoAudioError
BotSpeaking
 ├─ userSpeechDetected → Interrupting
 ├─ silenceWindow elapsed → BotSilent
 └─ completion → CompletionDeadPeriod
Interrupting
 ├─ serverAck + outputSilent → UserSpeaking
 └─ timeout → forceStopPlayback / recover

阈值不能只看一次 sample：需要 attack/release window、设备归一化、连续帧 debounce。Completion 后 dead period 防止音频尾巴或缓冲 drain 被误认为新一轮 speaking。FAR 应只在每个 turn 首次真实输出时记录一次。

1.10 Audio Burst 设计

目标是允许用户进入 Voice 后立刻讲话，即使媒体链路尚未 ready。客户端可用环形 buffer 暂存有限 PCM/encoded frames，ready 后快速 flush。

问题设计
缓存多久按产品容忍和内存预算设上限，例如 1–3 秒；超限丢最旧或停止并提示
时序每帧带 monotonic timestamp/sequence，服务端可重建顺序
重复切换 live stream 时以 sequence boundary 防止 burst 与实时帧重复
隐私仅在用户明确进入 Voice 后采集；失败/取消立即清空，不落盘
错误分类AudioBurstTimeout 与 DataChannelInitTimeout 分开，便于定位

1.12 Telemetry 字典

  • 客户端阶段：click、client_create、warmup_start/end、credential_ready、offer/answer、first_candidate、ice_connected、dtls_connected、datachannel_open、join_complete、audio_ready。
  • 媒体质量：RTT、jitter、packet loss、concealed samples、jitter buffer delay、audio level、selected candidate type、TURN usage。
  • 用户体验：click-to-ready、first-user-audio accepted、FAR、interruption latency、no-audio、session duration、unexpected disconnect。
  • 维度：host app、app/sdk version、device tier、OS、network type、candidate pair、region、feature flight；避免记录 PII。

语义原则：每个时间点注明发生层级：service emitted、client received、media decoded、system rendered 或 user-perceived proxy。名称相同但层级不同的数据不能直接比较。

1.13 协议级拷打与标准答案

WebRTC 一定使用 UDP 吗？

不一定。优先 UDP，但可通过 TURN/TCP 或 TURN/TLS 穿越受限网络。DataChannel 也不是 TCP，而是 SCTP over DTLS over ICE transport。

DTLS 和 SRTP 分别做什么？

DTLS 负责握手、对端证书 fingerprint 验证与密钥导出；SRTP 使用导出的密钥保护 RTP/RTCP 媒体。DataChannel 数据本身在 DTLS 中承载。

为什么 interruption 指标不能直接比较 WebSocket 与 WebRTC？

WebSocket 可能从服务端 audio chunk 到达开始计时；WebRTC 的 Speaking 可能来自系统输出 level，已经包含网络、jitter、decode 和 playback。必须使用共同的业务信号或同时保留分层指标。

ICE disconnected 与 failed 有何区别？

disconnected 常是暂态，可能自行恢复；failed 表示所有检查路径失败，通常需 ICE restart 或重建。产品还需结合持续时间和网络状态，不能仅凭一次 callback 立即销毁。

为什么 mute 必须发控制消息？

没有音频包可能是静音、网络丢包、设备故障或用户未说话。显式 mute 状态让服务端正确管理 turn 和超时；消息需版本化，避免乱序覆盖。

1.14 可防守的口述版本

我没有把 WebRTC 生产迁移描述成个人交付，而是针对 Mobile Copilot Realtime Voice 做了系统架构研究。我的分析重点是：迁移不是把 WebSocket 换成 PeerConnection，而是把音频放到 RTP/SRTP media plane，把 join、mute、transcript 和 telemetry 放到 DataChannel/control plane，并重新定义连接生命周期、Speaking/FAR、打断和指标语义。我重点设计了 warmup 失败不可复用、Audio Burst、网络切换后的 ICE/session recovery，以及分层 telemetry。为了验证理解，我能从 SDP/ICE/DTLS-SRTP 一直讲到 Android audio focus、状态机和故障 runbook，但不会声称拥有未实际交付的生产指标。
