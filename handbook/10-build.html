9. SharePoint BuildXL：大规模构建基础设施

不要只说“迁移构建脚本”。BuildXL/Domino 的核心是把每个进程建模为带声明输入输出的 Pip，构建形成 DAG；sandbox 观测文件访问，fingerprint 决定缓存命中，scheduler 利用依赖图并发和分布式执行。

9.1 核心模型

Source / Tool / Config ↓ declared inputs Process Pip ──→ declared outputs ↓ fingerprint Local Cache / Remote Cache ↓ miss Scheduler → Local or Distributed Worker ↓ observed file accesses / result / logs
PipFingerprint = Hash(
  executable + arguments + environment +
  declaredInputContentHashes + toolVersion +
  relevantConfig + directoryMembership
)

真实实现通常区分 weak/strong fingerprint：先用静态信息寻找候选，再结合动态观测输入确认。目录枚举、未声明文件、环境变量和工具自身行为都会影响可缓存性。

9.2 迁移难点

领域问题迁移方法
Metabuild生成项目/依赖图的工具本身也有输入输出先固定生成环境，输出稳定排序和路径
OACR/静态分析编译器 wrapper、额外文件访问、日志副作用显式声明工具链与输出，隔离非确定日志
Legacy scripts隐式读取 repo、TEMP、注册表、网络sandbox audit，逐步收紧 allowlist
Generated files时间戳、GUID、绝对路径造成内容变化移除非确定字段或规范化
Directory dependency目录新增无关文件导致整体失效缩小 glob/枚举范围，细化 seal directory

9.3 缓存正确性与命中率

错误命中比 miss 更危险：如果 Pip 实际读取了未声明输入，缓存可能复用旧结果。Sandbox/observed input 用于发现这种依赖。大量失效则常来自输入粒度过粗、工具版本漂移、路径和时间非确定性。

  • 通过 cache miss analyzer 比较两次构建 fingerprint 的差异。
  • 把“代码改变导致的合理 miss”和“环境噪声导致的非预期 miss”分开。
  • 远程 cache key 必须包含平台/toolchain 差异，避免跨环境错误复用。
  • 输出写入声明路径；多个 Pip 写同一文件会破坏 DAG 所有权。
拷打：为什么不把整个 repo 当一个输入？
正确性简单但任何文件变化都会让所有 Pip miss，失去增量和并发价值。需要在可维护性与依赖精度之间取舍，通过生成的 dependency graph 和目录封装降低声明成本。

9.4 Scheduler 与性能

总构建时间由关键路径而非 Pip 数量决定。优化包括减少关键路径串行依赖、提高 cache hit、平衡 CPU/内存/IO worker、避免超大 monolithic Pip。过度拆分会增加调度与上传开销，过度合并又降低并行和缓存粒度。

指标用途
Critical path duration识别真正决定 wall time 的 Pip
Cache hit rate（按耗时加权）比按 Pip 数计数更能反映收益
Queue/execute/materialize time区分调度、执行和缓存下载瓶颈
Remote bytes / cache latency判断远程 cache 是否反而拖慢小 Pip
Incremental build scenarios修改一个叶子、公共 header、配置的影响范围

9.5 Forward Integration

devmain→SpoRel FI 不只是 Git merge。需要确定变更集、解决冲突、生成新依赖图、跑受影响验证并区分源分支问题与目标分支环境差异。大规模 repo 中要避免“绿在源分支、红在目标分支”的工具链/配置漂移。

9.6 Build Break DRI

  1. 确认 break 范围：全局、特定 worker、特定 branch 或 cache corruption。
  2. 定位首个失败 Pip 和最早可疑 change，不被下游 cascade error 干扰。
  3. 选择 backout、roll-forward、禁用 cache entry 或基础设施缓解。
  4. 恢复主干优先，根因分析随后；记录 timeline、影响和检测缺口。
  5. 验证修复：clean build、incremental build、cache hit 和目标分支。
拷打：什么时候 backout，什么时候 roll-forward？
若影响广、根因不清、回滚安全且主干生产力受阻，优先 backout；若变更不可逆、已有依赖或修复明确且验证快，可 roll-forward。决策看恢复时间和二次风险，而不是个人偏好。

9.7 迁移与 rollout

  • Shadow build 对比旧新系统产物与测试，而不是一次切换。
  • 按 component/branch 分批；保留 fallback 和阻断阈值。
  • 比较 clean/incremental、正确性、cache、稳定性和开发者等待时间。
  • 为 unsupported access 建立例外清单和退出日期，防止永久宽松。

9.8 口述版本

我参与的不是简单脚本改写，而是把 SharePoint 大型代码库迁移到基于 Pip DAG、sandbox 和 content-addressed cache 的 BuildXL 模型。主要难点是把 legacy build 中隐式的文件、工具和环境依赖显式化，解决 metabuild、OACR、生成文件非确定性和目录粒度导致的 cache invalidation。我用 fingerprint/miss 分析区分合理失效与环境噪声，并围绕 critical path 而不是单纯 Pip 数优化增量构建。作为 Build Break DRI，我先隔离首个失败与影响范围，再在 backout 和 roll-forward 之间按恢复时间和风险决策。
