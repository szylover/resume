2. Voice 冷启动与连接性能治理

“冷启动优化”要讲成关键路径治理，而不是一句“加了预热”。先定义用户时间线：

T0 点击 Voice
T1 SDK/ACS 初始化
T2 credential/token ready
T3 client/session create
T4 Data Channel ready
T5 SetupAndJoin 完成
T6 microphone/audio ready
T7 first user audio accepted
T8 first bot audio rendered (FAR)

指标体系

主指标

  • Click-to-Ready P50/P95/P99
  • Session setup success rate
  • First Audio Render
  • Warmup hit / miss / invalidation rate
  • Text-but-no-audio、first-utterance loss

护栏指标

  • 内存常驻和后台电量
  • token 过期与凭据刷新
  • 重复 session 数
  • crash/ANR、线程/协程泄漏
  • 被预热但从未使用的浪费率

优化故事

定位
用 span 把 click-to-ready 分解到 SDK、credential、create、data channel、join 和 audio ready；按 cold/warm、network type、device tier、host app 分桶。不要只看平均值，重点看 P95/P99 和失败路径。
并行化
把可独立的 SDK init、credential fetch、config load 并行；把 create/configure/join 合并为 SetupAndJoin；提前建 early connection 和 Data Channel。
复用
缓存的不只是对象，而是带状态、TTL、网络 epoch、用户/tenant、config version 的可复用 session。任何 disconnect、warmup failure、账号/网络变化都应使其失效。
并发控制
多个入口同时触发 warmup 时用 single-flight 合并；真实 join 可复用同一个 Deferred，避免重复连接、竞争写状态和资源浪费。
上线
Feature Flag 分阶段：internal → 1% → 5% → 25% → 50% → 100%；每阶段看主指标和护栏，异常自动 kill switch。

Trade-off

选择收益成本/风险控制手段
预热缩短关键路径内存、电量、无效连接、凭据过期场景预测、TTL、后台策略、预算
缓存 client复用 SDK/sessionstale/disconnected client显式状态、health check、network epoch
并行初始化降低总延迟并发竞态、取消复杂structured concurrency、single-flight
SetupAndJoin减少 RTT服务端接口复杂、失败粒度变粗阶段 span、幂等 request id、可重试分类

2.1 Critical Path 分析

总时长不是所有阶段相加，而是依赖 DAG 最长路径。若 credential 与 SDK init 独立，可并行；但 join 依赖两者。先画 DAG，再优化最长路径，避免花时间优化不在 critical path 的小阶段。

click ├─ SDK init (280ms) ───────┐ ├─ credential (180ms) ─────┼→ client create (120ms) → join (350ms) → audio ready └─ config/feature (60ms) ──┘ 串行约 990ms；并行前三项后关键路径约 750ms（示意，非真实项目数据）

端到端 span 用 monotonic clock；跨客户端/服务端比较需要 clock sync 或使用同侧观测。每个阶段同时记录 success/failure/cancel/cache hit，不能只记录成功延迟形成幸存者偏差。

2.2 Cold/Warm 定义

类型定义用途
Process cold进程与 SDK 均未初始化最差启动体验
SDK warm进程/SDK 已初始化，无 session隔离 SDK init 成本
Client warmclient/DataChannel ready，未 join评估预热收益
Session resume已有可恢复 session评估恢复路径

如果把所有样本混在一起，预热提高 warm 样本比例会让总体 P50 变好，却可能掩盖 cold path regression。Dashboard 必须按 path 分桶，同时报告流量占比。

2.3 Warmup Eligibility

fun shouldWarmup(input: WarmupInput): Boolean = when {
    !input.featureEnabled -> false
    !input.userSignedIn -> false
    input.appInBackground -> false
    input.lowMemoryDevice -> false
    input.batterySaver -> false
    !input.networkValidated -> false
    input.existingHealthyClient -> false
    input.voiceEntryVisible || input.predictedClickProbability > 0.6 -> true
    else -> false
}

预测式预热要计算收益：ExpectedBenefit = hitProbability × latencySaved - memoryCost - batteryCost - serverCost。阈值按设备和网络动态调整，而不是所有用户一视同仁。

2.5 Tail Latency

P95/P99 常来自 DNS、token refresh、低端机、GC、线程争用和服务端排队。平均值优化不代表尾延迟改善。需要按阶段做 percentile contribution，并关联 trace。Timeout 不是越短越好：过短会把慢成功变成重试风暴；应根据用户预算和阶段分位数设置。

2.6 实验设计

  • 随机化单位按 user/session，避免同一用户跨组污染 cache。
  • 主指标 click-to-ready、setup success；护栏内存、电量、server allocation、crash。
  • 预热命中率必须定义为“预热后在 TTL 内真实使用且 client 健康”。
  • 观察期覆盖工作日/周末、网络和设备；逐阶段 rollout。
  • 自动回滚不仅看均值，还看 error、P99 和资源。

2.7 故障案例模板

案例：Warmup 初始化失败但对象仍被 Service cache。下一次用户点击 Voice 命中“已存在 client”分支，跳过完整初始化，导致 ready timeout。定位时 warmup hit rate 看起来变高，但 setup success 下降。修复是把 health 纳入复用 contract：失败/disconnected client 原子移出 cache，close 后重建；同时新增 warmup_failed_reused 防御指标和 fault-injection test。

2.8 拷打

为什么不在 App 启动时永远预热？

会竞争启动 CPU/IO、增加内存和电量，并制造大量从未使用的连接；凭据/session 还可能在点击前过期。应在更接近 Voice 意图的信号上触发，并受资源预算控制。

如何证明优化不是把耗时挪到更早？

同时报告用户可感知 click-to-ready 和总资源/预热成本；对未使用预热统计浪费。优化体验可以前移工作，但必须透明衡量整体成本。

SetupAndJoin 合并后怎么定位失败？

接口可以合并 RTT，但内部仍需阶段 span 和稳定 error taxonomy；服务端返回 stage/error，客户端记录 allocation、configure、join 的逻辑节点。

2.9 口述版本

我先把 Voice 冷启动定义为 click 到 audio ready 的端到端路径，并画出 SDK、credential、client、DataChannel 和 join 的依赖 DAG。优化不是单纯预热：独立阶段并行，SetupAndJoin 减少 RTT，single-flight 避免重复初始化，缓存 key 包含 user/tenant/config/network epoch，失败或 stale client 不可复用。预热只在入口曝光和资源允许时触发，并用 TTL 控制。实验同时看 P50/P95/P99、setup success、warmup hit，以及内存、电量和无效预热，防止只是把成本前移。
