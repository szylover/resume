7. Teams MeetApp：AI 会议平台

背景
会议数据来自 Graph、Substrate、conversation/thread 和 insights 等多源。产品要在 Teams Desktop 中提供 Upcoming/Recent/Missed、Recap、AI Tasks、陌生人洞察和跨会议摘要，但不同数据源的 ID、权限、时间范围和一致性模型不同。
Owner 范围
客户端数据与导航架构、API adapter、统一 domain model、Insight Builder、Recap deep link、Copilot streaming 入口、性能 telemetry 和调试工具。

7.1 数据架构

Graph Calendar ─┐ Substrate Meetings ─┼→ Source Adapters → Normalizer → Meeting Identity Resolver Conversation API ───┤ ↓ Insight/Tasks ──────┘ Canonical Meeting Model ↓ Cache / Classification / Insight Builder ↓ ↓ Upcoming/Recent/Missed Recap/Copilot
type MeetingKey = {
  tenantId: string;
  organizerId?: string;
  threadId?: string;
  joinUrlHash?: string;
  startTime: number;
};

type CanonicalMeeting = {
  key: MeetingKey;
  title: string;
  startTime: number;
  endTime: number;
  attendees: Attendee[];
  sourceVersions: Record<Source, string>;
  permissions: MeetingPermissions;
  recap?: RecapAvailability;
  insights: MeetingInsights;
};

Identity resolution：不能只用 subject+time 去重。优先 thread/meeting id；缺失时使用 join URL hash、organizer、时间容差等组合，并保留 confidence。误合并会把 A 会议摘要显示到 B 会议，比重复展示更严重，因此低置信度宁可不合并。

7.2 分类与一致性

视图规则示例边界
UpcomingendTime 尚未过去，按 start 排序跨时区、全天事件、取消/移动会议
Recent过去 N 天内且用户有访问权90 天扩展、迟到的 recap/recording
Missed受邀但未参加，并排除取消/无意义短会参会信号延迟、跨设备加入

多源数据最终一致：Calendar 先到，Recap/Tasks 后到。UI 需要 progressive enrichment，不能等待所有 source；但每次 patch 必须基于 meeting key 和 source version，防止旧请求晚到覆盖新数据。

function applyPatch(current: CanonicalMeeting, patch: MeetingPatch) {
  const known = current.sourceVersions[patch.source];
  if (known && compareVersion(patch.version, known) <= 0) return current;
  return {
    ...mergeBySource(current, patch),
    sourceVersions: { ...current.sourceVersions, [patch.source]: patch.version }
  };
}

7.3 Copilot 与 CrossMeetingCatchUp

用户选择多个会议后，客户端构造结构化 selection，不直接拼大段 prompt。服务端重新鉴权，获取 transcript/notes/tasks，再生成跨会议摘要。流式回答中的每个引用应保留 meeting provenance，用户点击可回到对应 Recap。

Selected Meetings → Permission Revalidation → Transcript/Notes/Tasks Fetch → Per-meeting normalization and token budget → Cross-meeting synthesis → Streaming blocks + citations → Client reducer / cancellation / retry

Prompt 与上下文取舍

  • 先按会议生成结构化 facts，再跨会议归并，降低长上下文混淆。
  • 按用户问题选择 transcript/notes/tasks，不默认加载全部内容。
  • 敏感会议、外部租户和无权限 recording 必须在模型调用前过滤。
  • 引用来源与生成文本分离，避免模型伪造 meeting link。

7.4 Streaming 与取消

sealed interface CatchUpState {
  data object Idle : CatchUpState
  data class Loading(val requestId: String) : CatchUpState
  data class Streaming(val requestId: String, val blocks: List<Block>) : CatchUpState
  data class Completed(val blocks: List<Block>) : CatchUpState
  data class Failed(val kind: ErrorKind, val partial: List<Block>) : CatchUpState
}

用户改变 selection 或关闭页面时，通过 requestId 取消旧流；旧 chunk 即使晚到也不能写入新请求。允许保留 partial answer，但 UI 要明确未完成。Retry 必须创建新 request generation，同时可复用已验证的 meeting context cache。

7.5 导航系统

Recap deep link 需要表示 meeting identity、目标 tab（AI Notes/@Mentions/Tasks/Recordings）和 fallback。不能把短 URL 字符串散落在组件中；应由 RouteBuilder 统一编码，Resolver 根据 host capability、meeting type 和权限选择内部 route、web fallback 或错误页。

拷打：为什么导航也算架构难点？
跨 host、channel meeting、短链和不同 Recap 能力会造成组合爆炸。集中 route contract 才能版本化、测试和降级，否则 UI 组件各自拼 URL，生产问题难以定位。

7.6 性能与调试工具

把一次用户打开页面分成 navigation、shell mount、cache hydrate、calendar fetch、insight fetch、classification、first render、enrichment complete。每个 span 带 correlationId、meeting count、source、cache hit 和 host version。

type PerfEvent = {
  correlationId: string;
  stage: 'navigation'|'cache'|'calendar'|'insights'|'render';
  startMs: number;
  durationMs: number;
  success: boolean;
  errorClass?: string;
};

毫秒级 Debug Tool 使用 ring buffer，支持过滤、导出和脱敏。生产日志不能记录标题、参会人或摘要正文。内存泄漏重点检查订阅未释放、全局 store 保留 meeting objects、定时器和 streaming listener。

7.7 Rollout 与测试

  • Feature flag 按 host/version/tenant 分层；旧路由和旧数据流保留 kill switch。
  • Contract tests 覆盖 Graph/Substrate schema 变化；golden tests 覆盖分类和 route。
  • 故障注入：某一 source 超时、权限撤销、迟到 patch、重复 meeting、stream 中断、账号切换。
  • 指标：first render、enrichment latency、navigation success、dedupe conflict、Copilot completion、citation click、memory。

7.8 口述版本

MeetApp 的核心难点不是做会议列表，而是把多个最终一致的数据源合成稳定的会议实体，并让 Recap 和 Copilot 都基于同一个 identity、权限和导航 contract。我从 source adapter、canonical model、versioned patch 和分类 pipeline 搭起数据层；页面先用 cache/calendar 快速首屏，再渐进补齐 insights。CrossMeetingCatchUp 使用结构化会议 selection、服务端重新鉴权和带 provenance 的 streaming blocks。为了定位生产延迟，我建立 correlation span 和脱敏日志工具，把导航、API、分类和渲染串起来。设计取舍是宁可低置信度不合并会议，也不冒错误合并导致数据泄露的风险。
